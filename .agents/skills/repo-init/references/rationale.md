# Rationale

Loaded from `repo-init/SKILL.md`. Read this file when the user asks why the skill works the way it does, or before changing the skill. The Hard rules in `SKILL.md` remain in force throughout.

* **Configure-only, never fetch.** Template acquisition (GitHub "Use this template", a copy, a clone) happens before any agent session; conflating acquisition with configuration would need network and ownership decisions this skill cannot verify.
* **The shipped `Workflow: <not recorded>` makes the undecided state explicit.** Every skill treats it as undeclared and falls back to `git-flow`, the strictest, so a consumer repo that never runs this skill inherits safety rather than permissiveness. Asking once here is what makes the line trustworthy for every downstream skill.
* **Provenance is checked even on a green checklist.** A manually configured template clone passes every step-1 box; skipping step 2 there would let it keep the template's history and remote forever. Provenance costs one look at the origin URL, and a repo with its own history is a no-op.
* **Local `commit.template` config over `--global`**: a machine-wide template would leak this repo's conventions into unrelated repositories. The template travels with the repo, and other checkouts opt in themselves.
* **Scaffolding is opt-in per item, not a bundle.** A docs-only repo needs no `scripts/`; a repo with no external reading needs no `references/`. The 6a selection keeps the default outcome identical to the pre-scaffolding skill: nothing is created unasked.
* **`references/` over `third_party/`, `external/`, or `vendor/`**: those names carry build-layout semantics (code the project embeds, builds, or ships), while this directory is reading material only, with no calls and no dependencies.
* **Archive excludes ship commented out.** In the template repository the listed paths are the product, and forge source downloads honor export-ignore. A consumer project wants them on, so its release tarballs omit dev and agent metadata. The step-6g pattern matches only a comment line that holds exactly one path followed by `export-ignore` (dot paths, directories, and root files such as `AGENTS.md` alike), never a prose comment. Writing to a temporary file and moving it back behaves the same with GNU and BSD `sed` and needs no perl, unlike `sed -i`; only the matched lines change.
* **Fresh start lists local tags and worktrees.** `rm -rf .git` deletes every commit reachable only from a local branch, a local tag, or a detached HEAD, every local branch or tag name that origin lacks (even one on a commit origin already has, which the commit log cannot show), every stash entry, and the administrative data of every linked worktree, which leaves those worktree directories orphaned. The evidence commands cover each of these so the gate can restate them.
* **Fresh start re-probes.** The new `.git` has no `origin` and no `commit.template`, so the step-1 results no longer hold: 6a offers the remote, and the step-1 skip of steps 3 to 5 is decided from a fresh probe.
* **Fresh start lists submodule repositories.** A submodule's repository lives under `.git/modules/`, so `rm -rf .git` deletes it and any commit made inside the submodule that was never pushed, including commits on its usual detached HEAD; the superproject's own evidence commands cannot see them. The evidence loop finds each repository by its `objects` directory and keeps only a parent that holds a `HEAD` file, so a submodule path with a segment named `objects` (`lib/objects`) is neither listed twice nor passed to git as a false repository.
* **Template updates go through `git-merge`.** `git-fetch` and `git-pull` are origin-only by design, so the user fetches the `template` remote and `git-merge` integrates `template/main`.
* **Nested-repo test by prefix.** Git Bash prints `--show-toplevel` as `D:/...` while `pwd` prints `/d/...`, so a text comparison reports a false nested repo; an empty `git rev-parse --show-prefix` holds only at the toplevel on every platform.
